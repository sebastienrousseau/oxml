# 0.0.4

Correctness and verification. No new API surface worth learning; a
substantial amount of previously-unverified behaviour is now verified,
and several things that were documented turned out not to be true.

## If you are upgrading

Nothing should break. `ErrorKind` gained a `Display` implementation,
which is additive.

Two documented behaviours were **wrong before and are correct now** —
if you relied on the documentation rather than on testing, check:

- The README claimed entity expansion was not supported and that an XXE
  document was rejected. Internal entities have been expanded for some
  time, and an XXE document parses with the entity expanded to nothing.
  The behaviour did not change in this release; the documentation did.
- The limits table in the README had seven of ten rows wrong. The
  values in the code were always the real ones.

## Fixed

- **XPath name tests ignored namespace prefixes.** `//x:item` selected
  every `item` regardless of namespace -- a wrong answer with no error
  attached. Prefixes are now resolved against bindings supplied to
  `XPath::compile_with_namespaces`, and an unbound prefix is a compile
  error.

  **This changes what existing expressions return.** An unprefixed name
  test now matches only nodes in no namespace, which is XPath 1.0's
  behaviour and every conforming engine's. If your document declares a
  default namespace, `//item` now matches nothing where it previously
  matched everything; bind a prefix to the URI instead.
- **`Error::line_column` could panic.** It sliced the input at the byte
  offset, so an offset inside a multi-byte character aborted the
  process from the error-reporting path. The parser does not emit such
  offsets — two million random inputs produced 1,999,999 errors and not
  one — but `line_column` accepts any `&str`, and a caller holding the
  original bytes of a transcoded document has offsets that no longer
  line up.

## Known defects, now documented

- **XML 1.1 line endings.** U+0085 and U+2028 are not treated as line
  terminators, which is the one W3C conformance test oxml rejects
  wrongly. See
  [the design note](../design/xml-1-1-line-endings.md).

## Verification

- W3C conformance: 2,449 of 2,557 decided (95.8%), 98.9% of the
  2,585-test suite reaching a decision, **zero panics**. Every
  remaining failure is the parser being too permissive; none is a
  wrong rejection.
- Coverage 97.4%, with the conformance harness no longer exempt from
  the floor.
- Six new examples, and a CI job that runs every example under coverage
  instrumentation and fails if any public function is not called by one
  of them.
- Every code block under `doc/` is compiled and run as a test.
- A CI check that the repo-root README and the crate README match —
  only one of them is compiled as doctests, and they had drifted by 121
  lines.
- `encoding.rs` went from 5% coverage by its own tests to 99.2%. A
  decoder sabotaged to substitute U+FFFD for unpaired surrogates left
  all 2,585 conformance tests green; the new unit tests fail
  immediately.
- The archive digest that pins the conformance suite is checked against
  the published FIPS 180-2 vectors, including the block-boundary cases
  where a hand-rolled SHA-256 actually breaks.

## Measured

- **4.13 allocations per node** (66,037 for 16,002 nodes), held to a
  ceiling by a test. The README previously said 2.0.
- A nine-level billion-laughs document is refused in **66 ms** under
  default limits and **25 µs** under `Limits::strict()`. If you parse
  untrusted XML under load, use `strict()`.

## Documentation

`doc/` now carries the architecture, security model, testing strategy,
conformance results, comparison, user guide, four migration guides,
seven ADRs and two design notes. The README went from 515 lines to
over 900, with a twenty-question FAQ.

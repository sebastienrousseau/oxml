# oxml suite 0.0.11 readiness

Assessment recorded 2026-10-17. **The satellites are not ready for a
lockstep 0.0.11 release.** This is a read-only assessment of the remote
release branches, not the stale local `main` checkouts. No satellite
files, branches or PRs were changed.

## Evidence snapshot

Each row names the exact PR head inspected. CI totals count all
reported checks, not only required branch-protection checks. They are
a snapshot, not a substitute for checking the eventual release commit.
All six satellite release manifests already declare Rust 1.89.0.

The version and dependency entries come from each repository's
`Cargo.toml` at the listed commit, fetched through the GitHub contents
API. Requirements such as `"0.0.10"` do not accept `0.0.11` under
Cargo's pre-0.1 compatibility rules. The MCP package version alone has
advanced; its dependency pins have not.

The inspected trees have no `doc/release-notes/` files. Five satellites
track both root and fuzz `Cargo.lock` files; `xmlschema` tracks neither
at the inspected head. Its locked dependency baseline must be prepared
before a repeatable release build can be certified.

## Blocking work

1. Prepare package metadata, lockfiles, current install examples and
   release notes for 0.0.11 in every satellite. Keep historical release
   records unchanged.
2. Advance the suite dependency requirements together. In particular,
   the CLI and MCP server must use the same `oxml` version through both
   their direct dependency and `xmlschema`; LSP also requires a matching
   `oxml-json` release.
3. Verify each consumer against the new core, not only the published
   0.0.10 interface. Review exhaustive `EvalError` matches and adopt
   explicit evaluation budgets at untrusted XPath entry points.
4. Resolve all failing CI checks and run each repository's own gate,
   audit, package inspection, issue triage and target-specific tests.
   Browser/Node execution is required for the WASM binding; a native
   build alone is not evidence for its JavaScript interface.
5. Confirm registry access and Trusted Publishing before any tag is
   pushed. An existing release workflow or a green PR cannot establish
   that the crates.io configuration is present.

The [CLI's Ubuntu test](https://github.com/sebastienrousseau/oxml-cli/actions/runs/38547992641/job/115798711652)
failed because the registry could not resolve `oxml = "^0.0.10"`;
it found 0.0.9 and older versions. This verifies that job's cause,
not every failure in the suite.

The historical core 0.0.10 publication workflow
[failed](https://github.com/sebastienrousseau/oxml/actions/runs/38177637260)
with HTTP 400: no Trusted Publishing configuration for this repository.
Its present authentication configuration and the full set of live
registry versions are UNKNOWN until verified independently. Do not
rewrite a published tag or retry a publication as a readiness check.

## Release order and limits of this assessment

Publish `oxml` before `xmlschema`; publish both before `oxml-cli` and
`oxml-mcp`. Publish `oxml` and the independent `oxml-json` before
`oxml-lsp`. `oxml-wasm` requires `oxml` only. This adds the JSON crate
that the former six-crate inventory omitted.

This assessment does not certify the satellites' vulnerability alerts,
issue triage, test coverage against 0.0.11, Node/browser behavior,
artifact provenance or hardware/RTOS execution. Those are UNKNOWN,
not passing. Core release preparation does not remove these blockers.

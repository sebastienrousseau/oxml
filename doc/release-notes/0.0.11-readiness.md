# oxml suite 0.0.11 readiness

Assessment updated 2026-10-17. **Publication remains blocked.** Local
release candidates now align all seven release crates and all nine
unpublished fuzz/conformance packages at 0.0.11. Family dependency
requirements are exact `=0.0.11`; every root/fuzz lockfile was resolved
with Cargo against the local family sources. The harnesses remain
`publish = false`.

All seven repositories have secret scanning and push protection enabled,
verified through GitHub's repository settings API. Separate Gitleaks
scans of all locally available Git refs found no leaks. Neither result
proves that every possible credential is detectable or that every
historical security-alert dismissal was a fix.

Six satellite changelogs and release notes are dated 2026-10-17. Local
integration work includes explicit input/evaluation budgets, dry-run-only
laptop publish helpers, and exact-source example-coverage checks with
negative regression contracts. These are local changes, not a claim
about the existing remote PR heads below.

The required release boundary is unchanged: publish/index prerequisites,
resolve registry-only locks, obtain human review and DCO certification,
and check CI on the resulting published heads. All seven Trusted Publisher
registrations were configured through the maintainer's laptop browser and
independently read back from crates.io as exact repository/release.yml
matches. Token-publishing enforcement was not changed. This verifies
registration, not a successful release-time OIDC exchange. No merge, tag
or publication is part of this preparation. Linux/Windows CI, WASM browser
execution and RTOS/hardware
behavior on the final candidates are not established by macOS/Node tests.

The maintainer approved the NCSA exception for the exact fuzz dependency
`libfuzzer-sys 0.4.13` and the core's signed-tag/Trusted Publishing policy
for all six satellites. The exception is confined to each fuzz workspace;
the root allowlists are unchanged. Satellite workflows verify the approved
public signer and exact project/version tag subject, then authenticate
through OIDC without a stored-token fallback. Real disposable-key fixtures
test rejection boundaries; they neither register publishers nor authorize
release tags.

The maintainer approved digest-pinned Scorecard execution without public
results publication. Workflows now select the provenance-verified v2.5.0
image by SHA-256 digest, disable publishing and remove OIDC permission.
SARIF artifacts and categorized GitHub posture findings remain available;
README badges show workflow status instead of a public score. Policy
contracts are checked locally and on pull requests. The new workflow's
actual GitHub execution and SARIF ingestion require fresh remote CI;
changing output destinations does not remediate historical posture issues.

Before these policy changes, all seven public release heads carried their
human DCO trailers. The new Scorecard changes need their own human review
and certification; prior certifications are not extended automatically.

## Release gates (the historical findings below are not current CI results)

1. Prepare package metadata, lockfiles, current install examples and
   release notes for 0.0.11 in every satellite. Keep historical release
   records unchanged.
2. Advance the suite dependency requirements together. In particular,
   the CLI and MCP server must use the same `oxml` version through both
   their direct dependency and `xmlschema`; LSP also requires a matching
   `oxml-json` release.
3. Verify each consumer against the new core, not only the published
   0.0.10 interface. Review exhaustive `EvalError` matches and adopt
   explicit evaluation budgets at untrusted XPath entry points.
4. Resolve all failing CI checks and run each repository's own gate,
   audit, package inspection, issue triage and target-specific tests.
   Browser/Node execution is required for the WASM binding; a native
   build alone is not evidence for its JavaScript interface.
5. Confirm registry access and Trusted Publishing before any tag is
   pushed. An existing release workflow or a green PR cannot establish
   that the crates.io configuration is present.

The [CLI's Ubuntu test](https://github.com/sebastienrousseau/oxml-cli/actions/runs/38547992641/job/115798711652)
failed because the registry could not resolve `oxml = "^0.0.10"`;
it found 0.0.9 and older versions. This verifies that job's cause,
not every failure in the suite.

The historical core 0.0.10 publication workflow
[failed](https://github.com/sebastienrousseau/oxml/actions/runs/38177637260)
with HTTP 400: no Trusted Publishing configuration for this repository.
The new registrations were independently verified for all seven crates;
none had version 0.0.11 published at that check. An actual release-time
authentication exchange remains unverified. Do not rewrite a published
tag or retry a publication as a readiness check.

## Release order and limits of this assessment

Publish `oxml` before `xmlschema`; publish both before `oxml-cli` and
`oxml-mcp`. Publish `oxml` and the independent `oxml-json` before
`oxml-lsp`. `oxml-wasm` requires `oxml` only. This adds the JSON crate
that the former six-crate inventory omitted.

The historical snapshot alone does not certify current vulnerability
alerts, issue closures, source coverage, Node/browser behavior or artifact
provenance. Later local evidence must be bound to the reviewed candidate
and must not be confused with registry-only or published CI results.
